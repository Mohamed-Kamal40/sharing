# Smapi Web SDK: IDs, Storage, Domain Cookies and User Session

This page covers how the Smapi Web SDK stores user identity, where it keeps it, and how the session id behaves. It covers the default behavior and every option that changes it.

Applies to: smapi-js v8.8.0 and later.

---

## 1. Summary

| Topic | Default behavior | Option that changes it |
|---|---|---|
| Where ids are stored | `localStorage` | `cookiesEnabled: true` stores them in cookies |
| Cookie scope | Host-only (only the exact host that set them, e.g. `app.example.com`) | `useDomainCookies: '.example.com'` shares them across sub-domains |
| Session id | One id per browser tab, kept in `sessionStorage` | `userSessionEnabled: true` shares one id across all tabs |
| Session expiry | Ends when the tab closes | `userSessionTimeout` (minutes of inactivity, default `30`) when `userSessionEnabled` is `true` |
| Id expiration | 1 year after the SDK loads | `expireTimestamp` |
| Who controls these settings | Only the main instance (the first instance initialized) | — |

If you set none of these options, the SDK behaves exactly as in releases before v8.8.0.

---

## 2. Ids the SDK keeps

| Storage key | Event field | What it is | Lifetime |
|---|---|---|---|
| `smapi_subject_id` | `x-vf-trace-subject-id` | Long-lived id for the user/browser. Created on the first event if missing. | Until `expireTimestamp` |
| `smapi_install_id` | `install-id` | Install id. When missing, the SDK uses the subject id as its value. | Until `expireTimestamp` |
| `smapi_session_id` | `x-vf-trace-session-id` | Session id. See [section 5](#5-session-id). | Per tab (default) or per user session |
| `smapi_session_last_activity` | — | Time of the last SDK event. Only used when `userSessionEnabled` is `true`. | Same storage as the session id |
| `smapi_previous_session` | — | Last session id seen. Used to count sessions for the rating modal. | Until `expireTimestamp` |
| `smapi_session_counts` | — | Number of sessions. The rating modal can show from the 5th session. | Until `expireTimestamp` |
| `smapi_rating_modal` | — | Set after the user answers the rating modal, so it is not shown again. | Until `expireTimestamp` |
| — | `x-vf-user-id` | The app's own user id. Comes from the `userId` config or `setUserID()`. The SDK never stores it. | Instance lifetime |

All ids are generated by the SDK as UUIDs.

## 3. Configuration reference

| Field | Type | Default | Description |
|---|---|---|---|
| `cookiesEnabled` | `boolean` | `false` | `true` stores the ids in cookies. `false` stores them in `localStorage`. |
| `useDomainCookies` | `string` | `''` (not set) | Domain to scope the cookies to, for example `'.example.com'`. Used only when `cookiesEnabled` is `true`. |
| `expireTimestamp` | `number` | SDK load time + 1 year | Absolute expiration time in milliseconds (a timestamp, **not** a duration). Applies to cookies and `localStorage` entries. |
| `userSessionEnabled` | `boolean` | `false` | `true` keeps one session id for the whole browser, shared by all tabs and windows. |
| `userSessionTimeout` | `number` | `30` | Minutes without SDK activity before a new session id is issued. Only used when `userSessionEnabled` is `true`. Must be greater than `0`. |

### Validation

`sec.init` rejects an invalid configuration with:

```
Incorrect configuration object, check value of field ==> <field name>
```

| Field | Rule |
|---|---|
| `cookiesEnabled` | Must be a `boolean` |
| `expireTimestamp` | Must be a `number` |
| `userSessionEnabled` | Must be a `boolean` |
| `userSessionTimeout` | Must be a `number` greater than `0` |

`useDomainCookies` is not validated. Pass a valid domain the current page belongs to, otherwise the browser rejects the cookies.

### Full example

```js
window.sec.init({
  // ...other config
  cookiesEnabled: true,
  useDomainCookies: '.example.com',
  expireTimestamp: new Date().setFullYear(new Date().getFullYear() + 1),
  userSessionEnabled: true,
  userSessionTimeout: 30, // minutes
});
```

## 4. Storage mechanism

### 4.1 localStorage (default)

With `cookiesEnabled: false`, ids are saved in `localStorage` as `{ value, expire }`. An entry past its `expire` time is treated as missing and the SDK creates a new id.

`localStorage` belongs to one origin, so `app.example.com` and `shop.example.com` always have different ids. `useDomainCookies` has no effect here.

### 4.2 Cookies

With `cookiesEnabled: true`, every SDK cookie is written with:

```
<name>=<value>; expires=<expireTimestamp>; [domain=<useDomainCookies>;] SameSite=Lax; path=/; Secure
```

- `Secure`: the browser only stores the cookie on HTTPS pages. On plain HTTP pages (other than `localhost` in some browsers) the cookie is not saved.
- `SameSite=Lax`: the cookie is not sent on cross-site sub-requests. The SDK reads it through `document.cookie` only, so this has no effect on tracking.
- `path=/`: visible to every path of the host.

### 4.3 Switching between localStorage and cookies

When the storage changes (at init, or through `setCookiesEnabled`), the SDK moves the existing ids to the new storage and removes them from the old one, so the user keeps the same identity:

| Key | Value in the new storage |
|---|---|
| `smapi_subject_id` | Copied |
| `smapi_install_id` | Copied. If missing, the subject id. |
| `smapi_previous_session` | Copied. If missing, the current tab session id. |
| `smapi_session_counts` | Copied. If missing, `1`. |
| `smapi_rating_modal` | Copied only if it exists |
| `smapi_session_id`, `smapi_session_last_activity` | Copied only when `userSessionEnabled` is `true` |

Nothing is moved if neither storage has a subject id yet.

### 4.4 Runtime API: `setCookiesEnabled`

```ts
setCookiesEnabled(value: boolean, expireTimestamp?: number, useDomainCookies?: string): void
```

```js
window.submitter.setCookiesEnabled(true);                          // move ids to cookies
window.submitter.setCookiesEnabled(false);                         // move ids back to localStorage
window.submitter.setCookiesEnabled(true, undefined, '.example.com'); // cookies + domain scope
```

- Only the main instance can call it. Other instances log `The main instance that only can change storage mechanism` and nothing changes.
- `expireTimestamp` is applied only if it is a valid number.
- `useDomainCookies` is applied only if it is a non-empty string. An empty value keeps the current domain.

## 5. Session id

### 5.1 Default: one session per tab (`userSessionEnabled: false`)

- The session id lives in `sessionStorage`, so each tab has its own id.
- A page reload keeps the id. A new tab, a new window, or closing the tab starts a new id.
- `userSessionTimeout` is ignored.
- At init, the main instance removes any `smapi_session_id` and `smapi_session_last_activity` left in cookies or `localStorage` by an earlier user-session setup.

### 5.2 User session (`userSessionEnabled: true`)

- The session id is stored with the other ids: in cookies if `cookiesEnabled` is `true`, otherwise in `localStorage`. All tabs read the same id.
- With `useDomainCookies`, all sub-domains share the session id too.
- Every SDK event updates `smapi_session_last_activity`.
- When more than `userSessionTimeout` minutes pass without an event, the next event creates a new session id.
- The id is also copied into the tab's `sessionStorage`, so code that still reads `sessionStorage` sees the same value.

### 5.3 Comparison

| | `userSessionEnabled: false` (default) | `userSessionEnabled: true` |
|---|---|---|
| Storage | `sessionStorage` of each tab | Cookies if `cookiesEnabled`, otherwise `localStorage` |
| New tab or window | New session id | Same session id |
| Page reload | Same session id | Same session id |
| Tab or browser closed | Id is gone | Id is kept and reused if still within the timeout |
| New session id issued | For each new tab | After `userSessionTimeout` minutes without SDK events |
| Shared across sub-domains | No | Yes, with `cookiesEnabled` + `useDomainCookies` |
| `userSessionTimeout` | Ignored | Inactivity window |

### 5.4 Turning it off again

When a site sets `userSessionEnabled` back to `false`, the stored session id is removed from cookies and `localStorage` on the next page load. Each tab goes back to its own id.

### 5.5 Effect on the rating modal

The rating modal counts sessions by comparing the session id with `smapi_previous_session`. Each new session id adds 1 to `smapi_session_counts`. The modal can appear from the 5th session.

- Default mode: every new tab counts as a new session.
- User session mode: only a new session after the inactivity timeout counts, so the modal appears later for the same usage.

## 6. Domain cookies and id migration

### 6.1 What it does

By default the SDK cookies are host-only: `app.example.com` and `shop.example.com` each have their own ids.

Set `useDomainCookies` to the parent domain to share the ids between all its sub-domains:

```js
window.sec.init({
  // ...other config
  cookiesEnabled: true,
  useDomainCookies: '.example.com',
});
```

Requirements:
- `cookiesEnabled` must be `true`. With `localStorage` the domain is not used.
- The page must be served over HTTPS (the cookies are `Secure`).
- The page host must belong to the domain. A cookie for `.example.com` cannot be set from `app.other.com`.

### 6.2 Migration of existing ids

A sub-domain that already has host-only Smapi cookies would otherwise end up with two copies of the same id. To avoid this, at init the SDK reconciles them:

1. Read the current values of the sub-domain cookies.
2. Delete the host-only cookies.
3. For each id:

| Situation | Result |
|---|---|
| The parent domain already has the id (set by another sub-domain) | The sub-domain adopts the parent id. Its own old id is discarded. |
| The parent domain has no id yet | The sub-domain id is promoted to the parent domain and becomes the shared id. |

After the migration only the domain cookies remain.

Migrated keys: `smapi_subject_id`, `smapi_install_id`, `smapi_previous_session`, `smapi_session_counts`, `smapi_rating_modal`.

### 6.3 Example rollout

1. `app.example.com` enables `useDomainCookies: '.example.com'` first. Its users have no parent cookies yet, so their existing ids are promoted to `.example.com`.
2. `shop.example.com` enables it later. A user who already visited `app` adopts the `app` ids. The old `shop` ids are dropped.
3. From then on both sites report the same `subject-id` and `install-id` for that user.

Impact: when a sub-domain adopts the parent ids, its users' old ids stop appearing in new events. Plan dashboards and user counts for this.

### 6.4 Turning it off

Removing `useDomainCookies` does not move the ids back to host-only cookies. The existing domain cookies stay readable from every sub-domain until they expire.

## 7. Multiple instances

These five settings are global, because all instances share the same ids:

`cookiesEnabled`, `useDomainCookies`, `expireTimestamp`, `userSessionEnabled`, `userSessionTimeout`

- Only the main instance (the first one initialized) applies them.
- A later instance with different `userSessionEnabled` / `userSessionTimeout` values logs:

```
userSessionEnabled/userSessionTimeout can only be set by the main instance. This instance requested (enabled: <x>, timeout: <y>m) but the active session settings from the main instance are (enabled: <a>, timeout: <b>m).
```

- A later instance that calls `setCookiesEnabled` logs `The main instance that only can change storage mechanism`.

Set these options on the main instance.

---

## 8. Recommended setups

**Recommended: always set `cookiesEnabled: true`.** Cookies keep the ids when the user clears `localStorage`, and they are required to share ids and sessions across sub-domains. The default (`cookiesEnabled: false`, `localStorage`) exists only for backward compatibility.

Recommended configuration:

```js
window.sec.init({
  // ...other config
  cookiesEnabled: true,              // recommended
  useDomainCookies: ".example.com",  // when the site has several sub-domains
  userSessionEnabled: true,          // one session across tabs and windows
  userSessionTimeout: 30,            // minutes
});
```

| Goal | Config |
|---|---|
| Keep current behavior (not recommended) | Set nothing |
| Stable ids (recommended minimum) | `cookiesEnabled: true` |
| Same user across sub-domains | `cookiesEnabled: true`, `useDomainCookies: ".example.com"` |
| One session across tabs | `cookiesEnabled: true`, `userSessionEnabled: true`, `userSessionTimeout: 30` |
| One session across tabs and sub-domains | `cookiesEnabled: true`, `useDomainCookies: ".example.com"`, `userSessionEnabled: true`, `userSessionTimeout: 30` |
